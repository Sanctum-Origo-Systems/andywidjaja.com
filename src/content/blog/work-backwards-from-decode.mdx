One of the agentic workflows my team owns reads input documents and writes a set of long, structured documents from them, with quality reviews and revisions along the way. Its output was clearly better than a plain agent with an LLM, but one full run took about 90 minutes, and getting the quality right often took several feedback rounds after follow-up discussions. Our users liked the output, but dreaded running it.

In this post, a "run" means one full pass: from the input documents to the finished package of requirements, architecture, reviews and summary.

Recently, while my team worked on other areas, I focused on performance. A run now takes 12 to 21 minutes depending on the agent harness, roughly 5x faster, with the same quality score. There was no single trick. It was a slow loop of instrumenting, changing one thing, and measuring again.

The solution that worked was one fact I had known for years and naively set aside: **reading is cheap and writing is slow.** The reason is the KV cache.

## What the KV cache taught me

A language model writes left-to-right one token at a time. To decide the next token, attention has to look at every previous token, in every layer. Each earlier token is represented there by two vectors, a key and a value. Without a clever approach, the model would recompute those keys and values for the whole sequence on every new token, and the cost would grow with the square of the length.

The KV cache is the clever engineering. The model computes the keys and values for each token once, keeps them in GPU memory, and on each new step computes them only for the newest token. Everything else is a read operation.

That one fundamental idea separates every LLM call into two very distinct phases:

- **Prefill.** The model reads the whole prompt in one parallel pass and fills the cache. Thousands of tokens go through at once, as large matrix multiplications. It is fast per token.
- **Decode.** The model writes the answer one token per pass. Each pass reads the model weights and the whole cache from memory to produce a single token. Decode is limited by memory bandwidth, not by compute. Nothing inside one response can run in parallel.

Inference providers take it one step further with prompt caching. They keep the cache for a repeated prefix between requests, so the next call skips most of prefill. An agent sends the same long context on every turn, so this matters a lot: in our runs, 83 to 95 percent of input tokens were cache reads.

Once I realized this, the lengthy runtime was no longer a mystery. I measured our two models from the agent's own transcripts: the larger one wrote about 112 tokens per second (about 9 ms per token), the smaller one about 161 tokens per second (about 6 ms). Decode accounted for 83 to 89 percent of all model time. One full run asks for about 150,000 output tokens. Written one after another, that alone takes about 18 minutes, before any thinking, tool call, or round trip.

That number is essentially a speed limit, and it sits below the application layer our team owns. My team doesn't run the models. My team can't make decode run faster. We can only change how many tokens we ask for, and how many of them are written at the same time.

## The part my team owns, on top of two constants

That changed how I saw the whole system. AI inference is the bottom layer, the harness runs on it, and our application building blocks run on the harness. My team owns the top layer. The two layers under our layer are constants.

- **AI inference is a constant.** We pick the model for each role and the reasoning effort level, but tokens per second is what our inference endpoint can give us.
- **The harness is a constant.** The tool that runs the agent decides how sub-agents launch and how many processes fit in memory. We can file issues and work around its limits, but we can't easily change it.
- **The application building blocks are ours.** What each step is asked to write, the order and shape of the steps, which work goes to sub-agents, which checks run as plain code. We can re-design them, re-arrange them, re-fit them to a harness, or re-write them.

The evidence materialized quickly. The same building blocks ran almost twice as fast in one harness as in another. Changes in one agent harness moved only that harness's number. Only changes to the building blocks our team owns moved both.

So the optimization rule for the whole initiative became: **spend fewer decode tokens, and spend them in parallel whenever possible.** The rest of this post is that rule applied with classic engineering principles: moving mechanical work from the model into deterministic code, parallelism, and dependency graphs.

## Measure first

Before changing anything, every workflow step writes a start marker and an end marker to a run log: a timestamp, the step name, and the event. Each run then gives four numbers: wall clock, time inside marked steps, the score from an automated quality check (out of 100), and how many times the agent stopped to ask for a permission.

The score is the guardrail. A change is kept only if the quality score holds. A faster run that produces worse output isn't faster. It's just shorter, with a quality regression.

## Fewer decode tokens: bookkeeping isn't reasoning

The first log showed the model spending a lot of its output on work that needed no reasoning: merging review findings into one list, tracking which questions were open, picking which fixes to apply by severity, deciding when a verification gate could pass.

Those are plain code. I moved them into a helper script that the agent calls between steps. The documents' content lives in JSON. The model keeps the parts that need reasoning: writing the documents, reviewing them, and deciding what a finding means.

The clarification step shows the effect. It went from several minutes to under one, once the script did the bookkeeping and the orchestrating model stopped writing between steps.

The KV cache view makes this easy to justify. Giving the model more to read is cheap, especially when it repeats. Asking it to write a list that a script could build costs real seconds at 6 to 9 ms a token.

## Read the inputs once, and keep the exact words

Every later step needs the input documents, and reading them again each time costs round trips and context. So one intake step reads them once and writes notes that the rest of the run can reference.

The notes are not a summary. For each fact they keep the source file and section, and they copy the key sentences word for word. Later steps quote those sentences directly, and a check confirms each requirement can be traced to a real source document.

This matters more than it looks. A summary is a lossy copy, and it is fast for the same reason it is risky: whatever it leaves out is gone for every later step, and nothing downstream can find it. A quality score computed from the summary will not notice the missing facts either. If you speed up the reading step, add a validation check that every requirement in the source shows up in the result.

## Spend them in parallel: shorten the longest chain

Decode can't run in parallel inside one response, but separate responses can run side by side. So wall clock is the decode on the **longest chain** of steps, plus the round trips on it. In one run, the individual model calls added up to twice the clock time, reading and writing together: about two calls running at once on average. That overlap is the speedup.

Running steps in parallel helps only when it takes work off that chain. Research and analysis run side by side. Independent sections of the documents are written side by side. Long reviews are split into groups.

How you launch the parallel work also matters. In a setup where the orchestrating agent launched each sub-agent itself, the main drafting step started at about minute 11. With a fixed workflow running the same steps, it started at about minute 5. Every launch went through the orchestrating model first, and that model writes at decode speed too. The whole run got about a third shorter, but the faster run also used lower effort levels, so not all of that slow performance gap is the launch path. The six minutes saved before the first real step is the clean part.

The last big step may be counter-intuitive: stop running in batches. A batch waits for its slowest member before the next batch starts. In contrast, a dependency graph starts each step the moment its own inputs are ready.

The score barely moved. The clock dropped by almost half, and each change is visible on its own. Lower effort means fewer thinking tokens, which are decode tokens too. A faster model lowers the time per token. Both are choices we make per step against the inference constant, with the score as the guard.

## Don't rewrite what didn't change

The first version of an output document is the big run. Most of the work after that is feedback: switch the vector store, add a download button. The naive approach is to rerun the whole thing with the feedback added. That is the most expensive way to change two things.

Instead, the run first identifies what the feedback will impact: which requirements, components and decisions. Then it updates only those sections, and a verification check confirms nothing outside the identified scope got updated. For the same two lines of feedback, the update now changes 15 files where it used to change 54. In another test, an update took about half the time of the first version.

Same rule as everywhere else: fewer decode tokens. The unchanged parts don't need to be written again.

## One run is an anecdote

Look at D and E. Same setup, three minutes apart. That puts the noise at about one and a half minutes either way, which means the restructured flow in D isn't clearly better than C yet. I wanted it to be. The numbers don't confirm that.

Results vary. Run the good results again before you trust them, and report the range.

## The log catches what tests miss

One run came back in 13 minutes with a score of 98. That looked like a win. The review log said otherwise: an agent harness update had silently removed the agent's ability to launch sub-agents, so the main orchestrator ran every review itself. The run was faster because it skipped the work, and the quality score alone didn't catch it.

Only the per-step log showed it. That's the same lesson as [the Observer](/blog/observer-builder): green (pass) sometimes isn't the same as working.

## Some constants stay constant

Not every idea worked. In one agent harness, each parallel step starts its own agent process, about 250 to 290 MB each, and on a laptop under memory pressure, it started queuing steps that should have run side by side in parallel. The agent harness can run several sessions inside one process, which would have fixed it. We tested it, and the agent harness turns that off on purpose for reasons outside our control.

## What I'd tell another AI engineer

1. Learn how the KV cache works. Reading is cheap. Writing is expensive.
2. Measure your tokens per second per model. That number, multiplied by your total output tokens, is your performance floor.
3. Treat the harness and inference as constants. Put your effort into the layer and building blocks you own.
4. Log every step's start and end before you change anything.
5. Find the output tokens that need no reasoning, and move them into deterministic code.
6. Shorten the longest chain. Use a dependency graph, not batches.
7. Pick the model and reasoning effort level per step, with a quality check as the guardrail.
8. Run and validate good results again. Report the range instead of a single metric number.
9. Read the inputs once, into notes that keep the source and the exact words. Check that nothing got left out.
10. On an update, change only what the feedback touches, and validate that nothing else got edited.

The same rules work outside design documents. For example, a status report is mostly tables, dates and links a script can populate, so let the model write only the summary and the risks. A long proposal can be generated as short structured items and be rendered, so feedback only changes a few items, not the whole file.

Today a full workflow run takes 12 to 21 minutes depending on which agent harness, down from about 90, with the same quality score as before. The newer models helped. They worked most optimally after we stopped asking them to do a job that can be done by deterministic code.
